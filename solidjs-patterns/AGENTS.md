# Solid 2 Patterns — Complete Reference

Generated from rules/ by bun run build. Do not edit this file directly.

# Reactivity and lifecycle

**Impact: CRITICAL**

Components run once; reactive reads belong in JSX, memos, or the compute half of an effect. Keep props and store reads lazy: use `props.name` or `() => props.name`, not a destructured snapshot. Use `untrack` only for intentionally one-time reads.

## Derive; do not write back

Compute derived values with `createMemo`, not effects that synchronize signals. Writes in component bodies, memos, and effect compute functions throw `REACTIVE_WRITE_IN_OWNED_SCOPE`. Event handlers, effect apply functions, timers, and `onSettled` are write locations. Draft mutations in a store's derive function are allowed; unrelated signal writes are not.

```tsx
import { createMemo, createSignal } from "solid-js";

export function Counter() {
  const [count, setCount] = createSignal(0);
  const doubled = createMemo(() => count() * 2);
  return (
    <button
      onClick={() => {
        setCount((n) => n + 1);
      }}
    >
      {doubled()}
    </button>
  );
}
```

## Setters are deferred

Updates batch automatically until the microtask flush. A read immediately after a setter sees the old value. Prefer carrying the local value into imperative work; use `flush()` sparingly at imperative integration boundaries or in tests. Do not add `batch` wrappers.

```ts
import { createSignal, flush } from "solid-js";

export function deferredRead() {
  const [count, setCount] = createSignal(0);
  setCount(1);
  const before = count(); // 0
  flush();
  return { before, after: count() }; // after: 1
}
```

## Split effects; return cleanup

`createEffect(compute, apply)` tracks only compute. Compute must be pure; apply is untracked and may perform side effects. Return cleanup from apply: `onCleanup` inside apply silently does not register. Use `createRenderEffect(compute, apply)` only for necessary pre-paint DOM work.

```ts
import { createEffect, type Accessor } from "solid-js";

export function subscribeRoom(room: Accessor<string>, connect: (id: string) => () => void) {
  createEffect(room, (id) => {
    const disconnect = connect(id);
    return disconnect;
  });
}
```

For multiple dependencies, return an object/tuple from compute. To skip the first apply, use a local first-run boolean; testing `previous === undefined` is ambiguous if `undefined` is a valid dependency. Previous-value seeds belong in default parameters, not an old positional initial-value argument.

## Setup after settling

Use `onSettled`, with a block body. Its callback may return cleanup or `undefined`, never a setter result, promise, or arbitrary value. `onCleanup` remains valid in owned component/root/directive setup.

```tsx
import { onSettled } from "solid-js";

export function FocusInput() {
  let input!: HTMLInputElement;
  onSettled(() => {
    input.focus();
  });
  return <input ref={input} aria-label="Name" />;
}
```

Nested `createRoot` scopes now dispose with their parent. Use `runWithOwner(null, () => createRoot(...))` only when a truly detached lifetime is intentional, and retain/dispose the root explicitly.

# Async data and actions

**Impact: CRITICAL**

## Async memos and local boundaries

An async memo replaces the resource tuple. Capture reactive inputs synchronously before awaiting; reads after `await` do not establish dependencies. Place every potentially not-ready read under a purposeful `<Loading>` boundary: without one, initial suspension can blank the render root, including navigation and other chrome.

```tsx
import { createMemo, Errored, isPending, Loading, refresh } from "solid-js";

export function Profile(props: { id: string; load: (id: string) => Promise<string> }) {
  const name = createMemo(() => props.load(props.id));
  return (
    <section>
      <button
        onClick={() => {
          void refresh(name);
        }}
      >
        Refresh
      </button>
      <Errored
        fallback={(error, reset) => <button onClick={reset}>Retry: {String(error())}</button>}
      >
        <Loading fallback={<p>Loading profile…</p>}>
          <p>{name()}</p>
          <small>{isPending(() => name()) ? "Updating…" : ""}</small>
        </Loading>
      </Errored>
    </section>
  );
}
```

`Loading` shows the first-load fallback and retains stale content during subsequent pending changes. Do not hide useful content behind manual refetch spinners. `isPending(() => value())` observes pending changes for that expression; a bare `refresh(value)` is a quiet re-ask, not a pending declaration. Use `affects(value)` inside an action when that work must declare affected data. Handle a rejected refresh promise if using it outside an error boundary/action.

`latest(accessor)` peeks at an in-flight value rather than the consistent displayed value; reserve it for intentional display-ahead affordances. Do not use it everywhere to bypass consistency. `refresh(target)` recomputes a memo/derived store/projection and returns a promise for settlement.

Use `<Reveal order="together">` to reveal sibling `Loading` slots together; default `order="sequential"` reveals in order. `order="natural"` lets a released nested group resolve independently. `collapsed` only applies to sequential reveal. Keep each slot's boundary close to its data, not around the whole application shell.

## Actions with optimistic state

`action` wraps a generator (or async generator), not an arbitrary async callback. `yield` async work so the transition includes it. Optimistic writes paint during the action and revert when it settles; derive the optimistic view from authoritative data and refresh that data after the server write. A plain optimistic value is not permanent persistence.

```tsx
import { action, createMemo, createOptimistic, refresh } from "solid-js";

export function createRenameModel(api: {
  read: () => Promise<string>;
  save: (name: string) => Promise<void>;
}) {
  const saved = createMemo(() => api.read());
  const [name, setName] = createOptimistic(() => saved());
  const rename = action(function* (next: string) {
    setName(next);
    yield api.save(next);
    yield refresh(saved);
  });
  return { name, rename };
}
```

For collections use `createOptimisticStore(() => authoritativeRows, [])`, then draft writes inside the action, followed by refresh of the authoritative source. The returned tuple mirrors `createStore`. Handle mutation failures at the event boundary; the optimistic overlay rolls back, but user-facing errors still need presentation.

## Choose the data layer deliberately

For an isolated read, an async memo plus `Loading` is enough. Keep TanStack Query when the application depends on shared keyed caching, deduplication, invalidation, pagination, persistence, or its devtools. Solid 2 handles async rendering consistency; it does not automatically supply a QueryClient cache or those tools. Do not remove a working cache solely to remove resource boilerplate. For Query v6 recipes, read [query.md](query.md).

These patterns work in an SPA. They do not require SolidStart, SSR, server functions, or a routing migration. Do not carry SolidStart 1.x `query`/`createAsync` recipes into Solid 2 without checking that integration's current API.

# TanStack Solid Query v6

**Impact: CRITICAL**

Target `@tanstack/solid-query@6.0.0-rc.5` (and matching devtools). Continue using `useQuery(() => options)`, `useMutation`, `useInfiniteQuery`, `QueryClientProvider`, and `useQueryClient`. Keep keys reactive and include every fetch input in the key; pass cancellation signals to fetchers. Keep the QueryClient stable for the app lifetime.

## A data read can suspend

`query.data` suspends when no data is ready; put normal consumers under `Loading` and errors under `Errored`. On invalidation/refetch, keep cached content visible; use `isFetching` for a subtle indicator, not an early return that hides the content. Solid already retains previous values; do not mechanically port `keepPreviousData`. Function placeholders no longer receive previous-data arguments.

**Trap:** a disabled query with no cache can suspend indefinitely. `query.data ?? fallback` does not guard it: the read suspends before `??`. Status reads (`isPending`, `isSuccess`, `status`, `isFetching`, `error`) do not suspend. Guard optional/disabled queries by status before reading data, or provide meaningful initial/placeholder data.

```tsx
import { useQuery } from "@tanstack/solid-query";

export function OptionalName(props: { id?: string; load: (id: string) => Promise<string> }) {
  const query = useQuery(() => ({
    queryKey: ["name", props.id],
    enabled: props.id !== undefined,
    queryFn: () => props.load(props.id!),
  }));
  return <p>{query.isSuccess ? query.data : "Select a person"}</p>;
}
```

For a local spinner, `<Show when={!query.isPending} fallback={...}>` can guard a data read. Do not put unguarded data reads in the shell outside its `Loading` boundary.

## Mutation API and atomic settlement

`mutate(variables)` returns a promise; `mutateAsync` and per-call callback options are gone. Use `await mutate(variables)` with try/catch for sequential event work. Configure shared callbacks in `useMutation(() => options)`. The old `onMutate` return-value rollback context is not available: do not return a snapshot and expect it as `onError`'s third argument.

Return/await invalidation from `onSuccess` to keep the mutation pending until fresh data arrives, allowing one atomic paint. Do not fire-and-forget that promise if freshness is part of success.

```ts
import { useMutation, useQueryClient } from "@tanstack/solid-query";

export function useRename(save: (name: string) => Promise<void>) {
  const client = useQueryClient();
  return useMutation(() => ({
    mutationFn: save,
    onSuccess: () => client.invalidateQueries({ queryKey: ["name"] }),
  }));
}
```

## Cache optimism must paint before the transition

In this RC, normal cache writes inside `onMutate`, or immediately before `mutate()` in the same unflushed tick, are held by the mutation transition. They do **not** paint optimistically. For shared cache optimism: cancel in-flight reads, capture a closure snapshot, write the cache, **flush**, then mutate; rollback on failure and invalidate for authoritative state. Local optimistic primitives can instead be written inside `onMutate` and are designed for transitions.

```ts
import { flush } from "solid-js";
import { useMutation, useQueryClient } from "@tanstack/solid-query";

type Item = { id: string; text: string };

export function useAddItem(save: (item: Item) => Promise<Item>) {
  const client = useQueryClient();
  const queryKey = ["items"] as const;
  let committed = false;
  const mutation = useMutation(() => ({
    mutationFn: save,
    onSuccess: () => {
      committed = true;
      return client.invalidateQueries({ queryKey });
    },
  }));
  let inFlight = false;
  async function add(item: Item) {
    // Serialize this list writer: snapshot rollback must not erase a later add.
    if (inFlight) return;
    inFlight = true;
    committed = false;
    try {
      await client.cancelQueries({ queryKey });
      const previous = client.getQueryData<Item[]>(queryKey);
      client.setQueryData<Item[]>(queryKey, (rows) => [...(rows ?? []), item]);
      flush();
      try {
        return await mutation.mutate(item);
      } catch (error) {
        // A refetch/callback failure after server success must not undo a committed write.
        if (!committed) {
          // undefined is not a cache update; restore an absent entry explicitly.
          if (previous === undefined) client.removeQueries({ queryKey, exact: true });
          else client.setQueryData(queryKey, previous);
        }
        await client.invalidateQueries({ queryKey });
        throw error;
      }
    } finally {
      inFlight = false;
    }
  }
  return { mutation, add };
}
```

The example serializes only this hook instance. If other components write the same key concurrently, use an app-wide per-key coordinator or operation-specific rollback, not a whole-list snapshot that can clobber another writer. Treat a failure during awaited invalidation separately from a server rejection when the API may already have committed. Reuse an existing app helper rather than duplicating this machinery in each component.

Cache observer updates are deferred too. In tests, await the DOM with `waitFor`/`findBy*`; use `flush()` at the explicit optimistic pre-mutation boundary, not indiscriminately after every operation.

# Stores and context

**Impact: HIGH**

Use signals for scalar state and stores for nested objects/collections with per-property tracking. Store properties are plain values (`state.name`, not `state.name()`). Keep the proxy live; destructuring is a snapshot. Use `snapshot(store)` when an external library needs plain data.

## Draft-first setters and projections

No path setters or `produce` wrappers: mutate the provided draft. Use `reconcile(next, key)` on a draft collection to preserve item identity; the key is a string/function, not a Solid 1 options object. Prefer memos for simple derivations and `createProjection` for read-only derived collections with structural sharing. `createStore(fn, seed)` provides a derived store plus a setter when local writes are actually required.

```ts
import { createStore, createProjection, reconcile, snapshot } from "solid-js";

type Todo = { id: string; text: string; done: boolean };

export function createTodos() {
  const [state, setState] = createStore({ todos: [] as Todo[] });
  const summary = createProjection(
    (draft) => {
      draft.total = state.todos.length;
      draft.done = state.todos.filter((todo) => todo.done).length;
    },
    { total: 0, done: 0 },
  );
  function replace(rows: Todo[]) {
    setState((draft) => {
      reconcile(rows, "id")(draft.todos);
    });
  }
  function toggle(id: string) {
    setState((draft) => {
      const todo = draft.todos.find((row) => row.id === id);
      if (todo) todo.done = !todo.done;
    });
  }
  return { state, summary, replace, toggle, export: () => snapshot(state) };
}
```

Projection draft mutation is the derivation API, not permission to write into arbitrary external signals inside a compute scope. Do not synchronize a derived value back into the source with an effect.

## Context is the provider

Render `<Context value={...}>`, not `.Provider`. A default-less context throws when missing; `useContext` already returns `T`. An explicit `undefined` provider value also counts as missing. Use a `null` default only for genuinely optional context, not to silence a required-provider error. Instantiate app state inside its provider for independent roots/tests rather than sharing a module singleton by accident.

```tsx
import { createContext, createSignal, useContext, type Accessor } from "solid-js";
import type { JSX } from "@solidjs/web";

type Theme = { dark: Accessor<boolean>; toggle: () => void };
const ThemeContext = createContext<Theme>();

export function ThemeProvider(props: { children?: JSX.Element }) {
  const [dark, setDark] = createSignal(false);
  const value = {
    dark,
    toggle: () => {
      setDark((value) => !value);
    },
  };
  return <ThemeContext value={value}>{props.children}</ThemeContext>;
}
export function ThemeButton() {
  const theme = useContext(ThemeContext);
  return <button onClick={theme.toggle}>{theme.dark() ? "Dark" : "Light"}</button>;
}
```

# Components, DOM, and control flow

**Impact: HIGH**

## Imports, props, and dynamic components

Core primitives and stores come from `solid-js`. Browser rendering (`render`, `Portal`, `dynamic`) and DOM types (`JSX`, `ComponentProps`) come from `@solidjs/web`. Renderer-neutral `Element` comes from `solid-js`. Set TypeScript `jsx: "preserve"`, `jsxImportSource: "@solidjs/web"`, and use `@solidjs/vite-plugin` for compilation.

Use `merge(defaults, props)` for reactive defaults, but remember explicit `undefined` **overrides** defaults. Use `omit(props, ...keys)` to forward remaining props and read picked props directly from `props`. Do not destructure reactive props or eagerly copy them with object spread. Resolve children once with `children(() => props.children)` only if inspecting/transforming them; otherwise render `props.children` directly.

```tsx
import { merge, omit } from "solid-js";
import { dynamic, type JSX } from "@solidjs/web";

export function Button(input: JSX.ButtonHTMLAttributes<HTMLButtonElement>) {
  const props = merge({ type: "button" as const }, input);
  const rest = omit(props, "class", "children");
  return (
    <button {...rest} class={["button", props.class]}>
      {props.children}
    </button>
  );
}

export function Slot(props: {
  component: (props: { label: string }) => JSX.Element;
  label: string;
}) {
  const Content = dynamic(() => props.component);
  return <Content label={props.label} />;
}
```

Hoist `dynamic` creation into component setup; do not create it inside a reactive JSX expression. Prefer this factory to deprecated `Dynamic`/`createDynamic` patterns.

## Keying defines identity

Choose deliberately; changing modes changes state preservation:

- `<For each={rows()}>`: item is a raw value, index is an accessor; identity follows the item reference.
- `<For each={rows()} keyed={false}>`: item is an accessor, index a number; identity follows the slot (replaces `Index`).
- `<For each={rows()} keyed={row => row.id}>`: both item and index are accessors; identity follows the returned key even when fetched objects are replaced.
- `<Repeat count={count()}>`: callback receives a numeric index; use for a count, not object identity.

```tsx
import { For, Repeat, Show } from "solid-js";

export function Rows(props: { rows: { id: string; name: string }[]; selected?: string }) {
  return (
    <>
      <For each={props.rows} keyed={(row) => row.id}>
        {(row, index) => (
          <p>
            {index() + 1}: {row().name}
          </p>
        )}
      </For>
      <For each={props.rows} keyed={false}>
        {(row, index) => <input aria-label={`Slot ${index}`} value={row().name} />}
      </For>
      <Repeat count={3}>{(index) => <span>{index}</span>}</Repeat>
      <Show when={props.selected}>{(selected) => <b>{selected()}</b>}</Show>
    </>
  );
}
```

`Show` and `Match` function children receive accessors by default; `Show keyed` receives the raw value and remounts on identity change. Do not read an accessor as if it were an object. Use `For` for stable list instances; `.map` is not an identity-preserving rendering primitive.

## Class arrays and event casing

Native elements accept class strings, arrays, and objects: `class={["base", props.class, { active: selected() }]}`. Native `classList` is gone. Use camelCase event props (`onClick`, `onInput`); lowercase `onclick` becomes an attribute. `on:`, `oncapture:`, `attr:`, `bool:`, and `use:` namespaces are gone. For native listener options, use a ref factory with explicit cleanup. Booleans use presence/absence rules.

## Ref callbacks are unowned; factories own setup

`ref={element => ...}` callbacks have no owner. Registering `onCleanup` there silently leaks listeners. For component setup, capture a ref then use `onSettled` with returned cleanup. For reusable directives, call an owned factory during setup that registers cleanup and returns the unowned element callback. Multiple refs use arrays.

```tsx
import { onCleanup, onSettled } from "solid-js";

export function listenClick(handler: (event: MouseEvent) => void) {
  let element: HTMLButtonElement | undefined;
  onCleanup(() => {
    element?.removeEventListener("click", handler, true);
  });
  return (next: HTMLButtonElement) => {
    element?.removeEventListener("click", handler, true);
    element = next;
    element.addEventListener("click", handler, true);
  };
}

export function NativeButton(props: { onPress: () => void }) {
  let button!: HTMLButtonElement;
  const click = listenClick(() => {
    props.onPress();
  });
  onSettled(() => {
    button.focus();
  });
  return (
    <button
      ref={[
        (element) => {
          button = element;
        },
        click,
      ]}
    >
      Press
    </button>
  );
}
```

## Preserve accessibility and component lifetime

Keep reactive conditions in JSX (`Show`/`Switch` or expressions), not an early return in component setup that freezes a branch. Use native buttons/links with accessible names, label form controls, preserve keyboard focus when panels update, and announce asynchronous status with a restrained `aria-live="polite"` region. Dialogs need focus containment, Escape dismissal, and focus restoration; prefer a Solid 2-compatible accessible primitive over hand-rolling it. These requirements do not disappear with the reactivity upgrade.

Keep third-party editor/chart/observer setup in `onSettled`, return its destroy/disconnect function, and feed updates through split effects rather than remounting the library. Use `lazy` plus a local `Loading` boundary for expensive routes/panels; preserve the SPA shell while code/data load.

# Testing and migration checks

**Impact: HIGH**

Target the real Solid 2 compiler/runtime, not a Solid 1 JSX transform with updated package types. Use `@solidjs/vite-plugin` (default export), `jsxImportSource: "@solidjs/web"`, and `@solidjs/testing-library@1.0.0-rc.2`. Use Vitest with a DOM environment for components; `bun test` alone does not apply Vite's JSX compiler. This repository's `bun run test` invokes Vitest.

```tsx
import { afterEach, expect, test } from "vitest";
import { cleanup, fireEvent, render, screen, waitFor } from "@solidjs/testing-library";
import { Counter } from "./reactivity-0";

afterEach(cleanup);

test("counter updates after the deferred write", async () => {
  render(() => <Counter />);
  fireEvent.click(screen.getByRole("button"));
  await waitFor(() => expect(screen.getByRole("button").textContent).toBe("2"));
});
```

The import above names this repository's generated example module; in an application, import your actual component. Use `flush()` for deliberately synchronous signal assertions; prefer `findBy*`/`waitFor` for DOM, query observers, and async work. Read signals outside component setup to test old-before-flush/new-after-flush semantics. Dispose roots/rendered components and clear each test's QueryClient; turn retries off for failure cases. `onSettled` is not a license for async callbacks returning promises; launch async work with explicit error handling.

Test the behavior, not just successful compilation:

- A split effect cleans up on dependency replacement and unmount, exactly once per subscription.
- Ref factory listeners stop firing after disposal, even when retaining the detached DOM node.
- Initial async data shows a **local** loading state; invalidation retains stale content and later displays fresh data without a fallback flash.
- Disabled/no-cache queries render the status-guard fallback instead of suspending indefinitely.
- Cache optimism paints before the server promise settles; a rejected write restores the snapshot. Awaited `onSuccess` invalidation keeps pending until fresh data lands.
- Stable keyed rows preserve instances when objects are replaced; optimistic actions revert overlays on settlement.

When migrating, run `solid-migration-assistant@0.2.1` first, but note its source-only scan skips Markdown samples and targets an earlier RC. Follow up with typecheck, compiled sample tests, and relevant browser integration checks. Do not weaken assertions or add blanket suppressions to force a green run. Verify emitted browser imports reference `@solidjs/web`, not `solid-js/web`.
